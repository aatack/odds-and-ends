# Topics mode

Written in ASD-STE100. An experiment, after chat apps. Code: `src/core/modules/topics/` (`view.ts` is pure, `topics.ts` writes and dispatches), `src/renderer/src/views/Topics.tsx`.

## Requirements

1. The UI has two modes. The topics mode is the default. The classic UI (the modules in the sidebar) is behind a flag: start the app with `DETAIL_VIEWS_UI=classic`. The main process gives the flag to the window as `?ui=classic` (`main.tsx` reads it).
2. Each mode keeps its own stack and selections (`detail-views.topics.state` and `detail-views.state` in local storage), so one mode does not change the other.
3. There is one global list of topics. Its root entity is `topics` (type `topics.home`). Each topic is an owned item of type `topic`, linked under the root. The ID of the topic is its entity ID. The name of the topic is its `text`.
4. On the left is the list of topics, in the place of the sidebar. Each topic shows its name and the time that it was last updated (`updatedAt`). Each is a light line, as a module is in the classic sidebar: muted text, its name darkening on a fill under the pointer; the open topic is on the selection's fill (`--select`). While Claude works in it, it shows the Claude mark and how long Claude has worked. The most recently updated topic is first (`byRecent`). A waiting topic (23) shows, as for Claude, what it waits on just left of its name (the Slack mark, the GitHub mark for a PR, a clock for a snooze (25), `⧗` for another topic, each kind once), and how long it has waited (since its oldest wait) in place of the time.
5. At the top of the list is a box: type a name and press Enter to make a topic (`topicCreate`). The new topic opens. **Ctrl+.**, from anywhere (typing too), opens a form for the name instead (`topic.new`, a `TopicDialog`), and a first path (14): The form has a **context** too: an item's id, whose context the new topic joins (`topicCreate` `context`, `Core.shareContext`; a context is made for them both if it has none). It starts as the task open, or the row selected in the thoughts open (`defaultTopicContext`), else blank; the item's pill shows beside it, and its × clears it, for a topic on its own. Enter makes the topic and opens it, Escape gives up. **`?`** on a topic (not while typing) opens the same form for a topic that also goes into the open topic's chat, as its pill (`topic.child`, `parent`); then the new topic opens.
6. A click on a topic opens its chat in the rest of the window. **`.`** (not while typing) opens the next topic down the list, round from the open one, in which Claude is not working (`topic.nextIdle`); it is disabled when there is none. The box of the chat does not have the keyboard, so the keys are free for other tools. Until I open a topic, the rest of the window is empty.
7. The chat is the chat page of the Claude module (`ChatPage` in `Claude.tsx`), `flat`, with no panel on the right: a flat list of the items directly under the topic, and the box at the bottom. My messages are lines on the left, across the width, with no bubble and no mark. Anything else linked into the chat (a file, a path, a PR, a branch, a Slack conversation, …) is its pill there (`ItemPill`: a hover peeks at it, a click opens it). Slack messages are not pills: they read as messages, so they show as their rows. Claude's answers are bubbles with the Claude mark beside them, a wash of Claude's colour (`--claude-soft`) inside an edge of it (`--claude-line`), and a small shadow. The mark lines up with the start of my messages, so Claude's bubbles are indented past it. Rows of one voice (mine, or Claude's) are close together (`joined`); between voices the gap is larger. The scroll bar is near the right edge of the window, with space between it and the messages. The chat and its box read in a column at most 840px wide, in the middle of a wider window; Claude's bubbles may take the whole column. Nothing in the chat is selectable: a click selects nothing, and the cursor keys and the item tools (Enter, `e`, `x`, …) do nothing there (`Session.selected` is null on a topic).
8. The box is always shown, but takes the keyboard only when asked (`ChatPage` `onDemand`). Enter gives it the keyboard (`topic.prompt`), as Tab does. Enter in the box when it is empty lets the keyboard go (`topic.leave`), as Escape does. Without the keyboard the box is faded and flat; with it, it is at full strength, its edge in the accent (`--accent-line`) and its inner shadow deeper.
9. Enter in the box (with text) adds a message to the chat, sends nothing, and lets the keyboard go. A message is a note (an item with no type) under the topic.
10. **Ctrl+Enter** (in the box or not) dispatches: if the box has text, it becomes a message first, and the box lets the keyboard go. Then all the messages since the last dispatch go to Claude as one prompt, separated by blank lines (`unsent`, `topicDispatch`). A response item (`claude.response`, `running`) goes under the topic after them, as a bubble on the left. It shows how long Claude has worked, then Claude's answer (or the error), as in the Claude module (`ask` in `claude.ts`).
11. Ctrl+Enter is disabled when there is nothing to send; then, on a topic, it says why ("Claude is still answering" or "Nothing new to send", `topic.dispatchRefused`) and does not go on to the side panel's Ctrl+Enter. The core refuses it too ("Nothing new to send"). While Claude answers (a response under the topic is `running`, `answering`), there is never a second dispatch: the core refuses it ("Claude is still answering"), and Ctrl+Enter only adds the text in the box as a message, which goes with the next dispatch.
12. The topic is the Claude session: its ID is the session ID. The first dispatch starts the session (`--session-id`); later dispatches resume it (`--resume`), and so does any dispatch once a transcript of it is where it runs (a dispatch killed part way leaves one). The topic keeps `started` and `runningSince`. Dispatches of one topic run one at a time, in sequence.
13. A dispatch runs in the topic's newest **path** (`latestPath`). When that is not where the topic ran before, the topic moves there first (`cwd`, and `worktree`, `branch`, `repo`, `origin`, `github` from the path, authored `claude`), and its transcript goes with it (`carryTranscript`), so the conversation resumes there. A topic with no path runs in its `cwd`; with neither, the first dispatch makes a new temporary directory and keeps it as `cwd` (authored `claude`, so undo does not remove it). A temporary directory of the app's (`claude-…` in the system's temp dir) that has gone, cleared on a reboot, is made again at the same path before Claude runs (`restoreTempDir`): Claude Code keeps the transcript by that path, so the conversation resumes. A directory of mine that has gone is not made again: the dispatch fails, saying so.
14. A **path** (type `path`) is a directory chosen for a topic, an item under it in the chat: its `text` the directory, and, for a new worktree, `worktree`, `branch`, `repo`, `origin`, `github`, as for a Claude session (`Claude.place`). It shows its directory with a folder mark, then "worktree of …" and its branch's pill. Adding one is `topicAddPath`: the directory must exist; it is remembered for next time (the Claude root's `cwds` and `repos`). A path alone is nothing to send (`unsent` leaves it out).
    - At the top right of the chat is a small button, **Path** (`PathPicker`). While I hover it, or after I press it (until I press it again), a card under it: a box to type a directory in (Enter adds it, `path.add`), and the directories I have used, most recent first, each a button that adds it as it is, with **Worktree** beside one in a git repo, which adds a new worktree of it on a branch of its own.
    - The new-topic form (Ctrl+.) has the same: a box for a path (optional), and the directories I have used, each with **Worktree**. Pressing a choice marks it (again: unmarks it). Enter makes the topic, with that path as its first item (`topicCreate` with `cwd`, `worktree`).
15. A paste outside a text box, while a topic is open and its box does not have the keyboard, goes into the topic as what it is (`paste.ts`, `topicPaste`, `topicAttach`):
    - A file (a copied file, a screenshot): kept under the app's data directory (`files/<id>/<name>`), as an item of type `file` (its `text` the name, `path`, `mime`, `size`) under the topic.
    - A link to a PR, a Slack message (`…slack.com/archives/<channel>/p<ts>`) or a GitHub branch (`github.com/<owner>/<repo>/tree/<branch>`): that item, linked under the topic. A PR and a Slack message load themselves. A branch (`github.branch`, id `github:branch:<owner>/<repo>:<branch>`) is all in its id and links to its page.
    - Any other text (another link too): a message with that text.
    - What is pasted goes with the next dispatch, in its place among the messages: a file as `[File: <path>]`, an item as `[Item: <id>]` (Claude reads it through the app's MCP server) (`promptPart`).
16. After each answer (not a failed one), when the topic's directory is a git checkout with changes not committed (`git status --porcelain`), the app asks Claude once to commit them (`commitPrompt`): a message of the app's own (authored `module`, so undo does not take it), and Claude's answer after it. It does not ask again after that answer. A dispatch is not over until this is done: Ctrl+Enter is refused until then.
17. After each dispatch, when the topic's directory is a git **worktree** (its git directory is not the repo's) on a branch (not a detached HEAD, not the remote's default branch) of a repo on GitHub, and that branch has a PR (the newest, `prOfBranch`: a read-only GraphQL query through `gh`), the PR's item goes into the chat, once, and into the topic's context (`Core.shareContext`, authored `claude`). A branch with no PR (one only here, or not pushed) adds nothing.
18. **Resolve** (a button beside Path; `topic.resolve`, no key) takes the topic out of the list: its link from the root is undone (the topic is kept, with `resolved`). The window is then empty. Not while Claude answers.
    - It removes the topic's worktrees (its own, and its paths'), each only when it is provably one the app made (`provenWorktree`): `worktree` is under the app's own `worktrees` directory, exists, is the top of a checkout, and the repo (`repo`) lists it in `git worktree list`. Any other directory (a temporary one, one of mine) is never removed. The branch is kept.
    - First it checks the worktree for work that would be lost (`topicResolveCheck`): changes not committed, commits not on any remote, commits not merged into the default branch. If there is any, a form lists it: Enter resolves anyway (`git worktree remove --force`), Escape keeps the topic. The core refuses without `force` too.
19. Beside **Path** at the top right are three git buttons (`topic.checkout`, `topic.master`, `topic.push`; no keys). Each acts on where the topic works now: its newest path, or else where it last ran (`where`). The *base repo* is the repo its worktree is of (`repo`), or else the one its directory is in. Each says what it did, or why not, as a toast.
    - **Check out**: the worktree's commit, checked out detached in the base repo (git will not check out a branch that another worktree has). Only with a worktree.
    - **Master**: the default branch (the remote's, else `master`) checked out in the base repo.
    - Both are refused while the base repo's checkout has changes not committed.
    - **Push**: `git push -u origin <branch>` from the worktree (or the directory): the branch, made on GitHub if new; never forced. Refused on a detached HEAD, on the default branch, to an `origin` not on GitHub, and while Claude answers. Then the branch's PR, if it has one, joins the topic (17).

20. **Where the box sends.** By default, Enter in the box adds a note. **Tab** in the box goes to the next place it can send, then back to a note (`topic.target`, `sendTargets`). The places come from the Slack items in the chat, each once, in the chat's order:
    - A message in a thread: a reply in that thread.
    - A message in a conversation: a reply in its thread, or a message to the conversation.
    - A conversation (a pasted `…slack.com/archives/<channel>` link): a message to it.
    - A message that has not loaded yet gives no place, because the app cannot tell if it is in a thread.
21. While the box sends to Slack, it has the warning's colours (`--warning-soft`, `--warning-line`), and the Slack mark and the conversation's name (with "thread" for a thread) are on its right. Enter sends the text to Slack as me, and links the message into the chat (`Core.topicSlackSend`). Then the box goes back to a note, so a second Enter cannot send again. If the send fails, the text comes back. Ctrl+Enter with text in the box does not send it to Claude: it says why (`dispatchRefusal`). The choice is not persisted: after a restart, the box adds a note. Just above the box is that place's overview (the thread's first message, or the conversation; `TargetOverview`), in the warning's colours too.
22. **Only I send to Slack** (`docs/slack.md`). `chat.postMessage` is the only write. Only a call with `byMe` (`api.ts`) can make it, and only `Core.topicSlackSend` gives `byMe`. That method is not in `Core.actions`, so the phone, the MCP server and Claude cannot call it. Only the window's own IPC channel (`slackSend`) calls it, and the window sends only immediately after a key press or click of mine (`navigator.userActivation`). The core sends only to a place that a Slack item in the topic gives.
23. **Waits.** A topic's `wait` is a list of what it waits on: `{ slack, since, dismissed? }` or `{ topic, since }` or `{ pr, since }` or `{ until, since }` (a snooze, 25). `slack` is a conversation (`slack:conv:…`) or a thread (its first message). `since` is when the wait started (Unix ms). Later kinds of wait go beside `slack`. `topic` is another topic: the wait is back once that topic is resolved; it brings nothing in to add (`waitReturned`). `pr` is a PR: the wait is back while it needs me (`prBackReasons`, by the GitHub view's `blockers`). Merged or closed: back. Mine: it waits while CI runs, someone else's review is all that is left, or it merges itself; it is back for anything I must do (conflicts, CI failing, changes asked for, threads, my own review, ready to merge). Someone else's: it is back only while it wants my review (requested of me, or neither approved nor changes asked for by me) and is not a draft; anything else on it is theirs.
    - On a hover over a Slack message in the chat, buttons show: wait on its **Thread**, its **Channel**, or **Both** (`topicWait`). A conversation in the chat shows **Wait**. Another topic or a PR in the chat shows **Wait**.
    - What came into a wait (`waitCandidates`): in a conversation, its top-level messages; in a thread, its replies. Only the ones after `since`. Not mine, not one already in the topic, not one I dismissed, not a join or a leave.
    - A topic is **waiting** (`waiting`) when it has waits and none is back. `.` does not go to a waiting topic. In the list, a waiting topic shows what it waits on and for how long (4).
    - It is worked out from the cache. The Slack watch (every 15 s) puts most new messages there; on top of that, after each of the watch's polls, each Slack wait is loaded on its own (`pollSlackWaits`): a thread whole, or a conversation's messages since the wait started. A PR wait is loaded on a backoff, back or not (a PR can go back to waiting: once I approve it, say) (`pollWaits`, `waitPollEvery`, checked every 30 s): every 2 minutes for the first hour, every 15 minutes for the first day, then every hour. A topic's wait is not loaded. Nothing is loaded for Slack while the watch is paused.
24. Above the box of a topic with waits is a box of them (`TopicWaits`): for each wait, the Slack mark, the conversation or thread, and how long it has waited (or how many new messages there are), and a × that stops it (`topicUnwait`). Under each wait are the messages that came in: **Add** links one into the topic; **Dismiss** keeps it out (`topicDismiss`). When I add or dismiss all of them, the topic waits again, until I remove the wait.
25. **Snooze.** While the box is empty and adds a note (not Slack), a clock is at its right (`topic.snooze`, no key). It opens a form for how long: `30m`, `6h`, `2d` or `1w` (minutes, hours, days, weeks; `snoozeLength`). Enter snoozes the topic, Escape gives up; the form's button is disabled until the length reads. A snooze is a wait `{ until, since }` (`topicSnooze`): back once `until` has come. A topic has one snooze at most: a new one replaces it. Its `waitOn` is `snooze`. Nothing is loaded for it. The window works out the waits again when a snooze ends, with no change to the cache. In the box of waits (24), it shows the clock, "Snoozed", and when it ends ("snooze over" once it has); × takes it away.
26. **Two displays.** A topic is a **task** (all of the above: a chat with Claude) or **thoughts**: a tree of notes, as entity-graph's editor draws one. It is kept as the topic's `display` (`'thoughts'`; none is a task; `displayOf`, `isTaskTopic`). The new-topic form (5) chooses: **Task** or **Thoughts**; the box at the head of the list makes a task.
    - Thoughts are the classic tree (`TreePane`, with the `thoughts` look), drawn exactly as entity-graph's editor draws one (`ThoughtsRow` in `View.tsx`, `--eg-*` tokens and `.eg-*` rules in `styles.css`, its values copied from entity-graph's `Editor.tsx`, `TextEditor.tsx` and `index.css`): every row, the topic's own first, indented 20px a level (`depth * 20 + 4`), 1px apart and 2px inside, 8px in from the sides, with 6px corners; a 20px square leads it with a 4px dot, a chevron while it has children (a click there folds it), or a box (kept even with children); its text in Lora (weight 450) 14px on a 20px line, gray-400 while its children are hidden, "Empty" in italics when it has none; a section in 600, `14 × max(1.1, 1.5 − 0.1 × depth)` px on a 1.3 line; hover gray-100 at 70%, selection blue-100; the chrome in Geist 14px; markdown as entity-graph's `.markdown`. Typing in place is entity-graph's frameless textarea in the row's own type, growing with what is typed (Enter writes, Shift+Enter breaks the line). Only the width is this app's: the task chat's 840px column, in the middle. The rows are selectable and worked as in any tree (Enter, `e`, `b`, `x`, folds, …; `Session.selected` is not null there).
    - Nothing of Claude's applies: no box, no dispatch, no path (the form hides it), no git buttons, no Slack from the box, no pastes into the chat. The core refuses them too (`Topics.task`: "Only a task topic works with Claude, paths and git"; `topicCreate` with `display: 'thoughts'` and a `cwd`).
    - At the top right: the snooze clock (25) and Resolve; above the tree, its waits (24).
27. **Ctrl+L** (from anywhere, typing too; `topic.jump`) opens a form to find a topic in the list by its name (`JumpForm`): what is typed matches fuzzily, every character in order, case aside; runs, the starts of words and an early match rank higher (`fuzzyScore`, `fuzzyRank` in `view.ts`); nothing typed lists them all, in the list's order. ↓ / ↑ move through the matches (`jump.down`, `jump.up`), Enter opens the one marked, a click any, Escape gives up.
28. **Hide snoozed.** Beside the box at the head of the list is a clock (`topics.hideSnoozed`, no key): pressed in, the list leaves out the topics snoozed now (`snoozed`: a snooze not yet over), except the one open; pressed again, they come back. It is kept (`hideSnoozed`, persisted with the mode's state). A snooze that ends brings its topic back into the list. Their waits are still watched, and Ctrl+L finds only what the list shows.

## Key decisions

- **A message is a note, not a new type.** The MCP server reads it as any note. The chat does not select it, so the item tools do not work on it there.
- **The chat is flat.** No notes under messages, so Enter needs no meaning on the rows: it moves the keyboard between the box and the chat.
- **The response marks the dispatch.** The messages to send are the notes after the newest response. No other marker is necessary.
- **Topics is also a module.** Its root is in `moduleViews`, so the classic UI shows it in the sidebar, and a headless caller can use it. The classic UI shows a topic as its chat too (`Detail`).
- **A wait is read off the cache, and loaded with the watch.** The watch finds most new messages across Slack, but search lags and can miss some, so a wait also loads its own conversation or thread, with every poll: an answer comes in as soon as anything else does. (It was a backoff, every minute down to hourly; too slow for an answer.) It is the one exception to the rule that the app never loads conversations one by one on its own, and only for a wait I set.
- **A wait is up while something new is not handled.** When I add or dismiss what came in, it waits again; it stops only with ×.
- **The phone stays on the classic UI.** It can open a topic and dispatch (the tool has a label), but it cannot make a topic.
