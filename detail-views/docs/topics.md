# Topics mode

Written in ASD-STE100. An experiment, after chat apps. Code: `src/core/modules/topics/` (`view.ts` is pure, `topics.ts` writes and dispatches), `src/renderer/src/views/Topics.tsx`.

## Requirements

1. The UI has two modes. The topics mode is the default. The classic UI (the modules in the sidebar) is behind a flag: start the app with `DETAIL_VIEWS_UI=classic`. The main process gives the flag to the window as `?ui=classic` (`main.tsx` reads it).
2. Each mode keeps its own stack and selections (`detail-views.topics.state` and `detail-views.state` in local storage), so one mode does not change the other.
3. There is one global list of topics. Its root entity is `topics` (type `topics.home`). Each topic is an owned item of type `topic`, linked under the root. The ID of the topic is its entity ID. The name of the topic is its `text`.
4. On the left is the list of topics, in the place of the sidebar. Each topic shows its name and the time that it was last updated (`updatedAt`). Each is a light line, as a module is in the classic sidebar: muted text, its name darkening on a fill under the pointer; the open topic is on the selection's fill (`--select`). While Claude works in it, it shows the Claude mark and how long Claude has worked. The most recently updated topic is first (`byRecent`).
5. At the top of the list is a box: type a name and press Enter to make a topic (`topicCreate`). The new topic opens. **Ctrl+.**, from anywhere (typing too), opens a form for the name instead (`topic.new`, a `TopicDialog`), and a first path (14): Enter makes the topic and opens it, Escape gives up.
6. A click on a topic opens its chat in the rest of the window. **`.`** (not while typing) opens the next topic down the list, round from the open one, in which Claude is not working (`topic.nextIdle`); it is disabled when there is none. The box of the chat does not have the keyboard, so the keys are free for other tools. Until I open a topic, the rest of the window is empty.
7. The chat is the chat page of the Claude module (`ChatPage` in `Claude.tsx`), `flat`, with no panel on the right: a flat list of the items directly under the topic, and the box at the bottom. My messages (and what I pasted) are lines on the left, across the width, with no bubble and no mark. Claude's answers are bubbles with the Claude mark beside them, a wash of Claude's colour (`--claude-soft`) inside an edge of it (`--claude-line`), and a small shadow. The mark lines up with the start of my messages, so Claude's bubbles are indented past it. Rows of one voice (mine, or Claude's) are close together (`joined`); between voices the gap is larger. The scroll bar is near the right edge of the window, with space between it and the messages. The chat and its box read in a column at most 840px wide, in the middle of a wider window; Claude's bubbles may take the whole column. Nothing in the chat is selectable: a click selects nothing, and the cursor keys and the item tools (Enter, `e`, `x`, …) do nothing there (`Session.selected` is null on a topic).
8. The box is always shown, but takes the keyboard only when asked (`ChatPage` `onDemand`). Enter gives it the keyboard (`topic.prompt`), as Tab does. Enter in the box when it is empty lets the keyboard go (`topic.leave`), as Escape does. Without the keyboard the box is faded and flat; with it, it is at full strength, its edge in the accent (`--accent-line`) and its inner shadow deeper.
9. Enter in the box (with text) adds a message to the chat, sends nothing, and lets the keyboard go. A message is a note (an item with no type) under the topic.
10. **Ctrl+Enter** (in the box or not) dispatches: if the box has text, it becomes a message first, and the box lets the keyboard go. Then all the messages since the last dispatch go to Claude as one prompt, separated by blank lines (`unsent`, `topicDispatch`). A response item (`claude.response`, `running`) goes under the topic after them, as a bubble on the left. It shows how long Claude has worked, then Claude's answer (or the error), as in the Claude module (`ask` in `claude.ts`).
11. Ctrl+Enter is disabled when there is nothing to send; then, on a topic, it says why ("Claude is still answering" or "Nothing new to send", `topic.dispatchRefused`) and does not go on to the side panel's Ctrl+Enter. The core refuses it too ("Nothing new to send"). While Claude answers (a response under the topic is `running`, `answering`), there is never a second dispatch: the core refuses it ("Claude is still answering"), and Ctrl+Enter only adds the text in the box as a message, which goes with the next dispatch.
12. The topic is the Claude session: its ID is the session ID. The first dispatch starts the session (`--session-id`); later dispatches resume it (`--resume`). The topic keeps `started` and `runningSince`. Dispatches of one topic run one at a time, in sequence.
13. A dispatch runs in the topic's newest **path** (`latestPath`). When that is not where the topic ran before, the topic moves there first (`cwd`, and `worktree`, `branch`, `repo`, `origin`, `github` from the path, authored `claude`), and its transcript goes with it (`carryTranscript`), so the conversation resumes there. A topic with no path runs in its `cwd`; with neither, the first dispatch makes a new temporary directory and keeps it as `cwd` (authored `claude`, so undo does not remove it).
14. A **path** (type `path`) is a directory chosen for a topic, an item under it in the chat: its `text` the directory, and, for a new worktree, `worktree`, `branch`, `repo`, `origin`, `github`, as for a Claude session (`Claude.place`). It shows its directory with a folder mark, then "worktree of …" and its branch's pill. Adding one is `topicAddPath`: the directory must exist; it is remembered for next time (the Claude root's `cwds` and `repos`). A path alone is nothing to send (`unsent` leaves it out).
    - At the top right of the chat is a small button, **Path** (`PathPicker`). While I hover it, or after I press it (until I press it again), a card under it: a box to type a directory in (Enter adds it, `path.add`), and the directories I have used, most recent first, each a button that adds it as it is, with **Worktree** beside one in a git repo, which adds a new worktree of it on a branch of its own.
    - The new-topic form (Ctrl+.) has the same: a box for a path (optional), and the directories I have used, each with **Worktree**. Pressing a choice marks it (again: unmarks it). Enter makes the topic, with that path as its first item (`topicCreate` with `cwd`, `worktree`).
15. A paste outside a text box, while a topic is open and its box does not have the keyboard, goes into the topic as what it is (`paste.ts`, `topicPaste`, `topicAttach`):
    - A file (a copied file, a screenshot): kept under the app's data directory (`files/<id>/<name>`), as an item of type `file` (its `text` the name, `path`, `mime`, `size`) under the topic.
    - A link to a PR, a Slack message (`…slack.com/archives/<channel>/p<ts>`) or a GitHub branch (`github.com/<owner>/<repo>/tree/<branch>`): that item, linked under the topic. A PR and a Slack message load themselves. A branch (`github.branch`, id `github:branch:<owner>/<repo>:<branch>`) is all in its id and links to its page.
    - Any other text (another link too): a message with that text.
    - What is pasted goes with the next dispatch, in its place among the messages: a file as `[File: <path>]`, an item as `[Item: <id>]` (Claude reads it through the app's MCP server) (`promptPart`).
16. After each answer (not a failed one), when the topic's directory is a git checkout with changes not committed (`git status --porcelain`), the app asks Claude once to commit them (`commitPrompt`): a message of the app's own (authored `module`, so undo does not take it), and Claude's answer after it. It does not ask again after that answer. A dispatch is not over until this is done: Ctrl+Enter is refused until then.
17. After each dispatch, when the topic's directory is a git **worktree** (its git directory is not the repo's) on a branch (not a detached HEAD, not the remote's default branch) of a repo on GitHub, and that branch has a PR (the newest, `prOfBranch`: a read-only GraphQL query through `gh`), the PR's item goes into the chat, once, and into the topic's context (`Core.shareContext`, authored `claude`). A branch with no PR (one only here, or not pushed) adds nothing.
18. **Resolve** (a button beside Path; `topic.resolve`, no key) takes the topic out of the list: its link from the root is undone (the topic is kept, with `resolved`). The window is then empty. Not while Claude answers.
    - It removes the topic's worktrees (its own, and its paths'), each only when it is provably one the app made (`provenWorktree`): `worktree` is under the app's own `worktrees` directory, exists, is the top of a checkout, and the repo (`repo`) lists it in `git worktree list`. Any other directory (a temporary one, one of mine) is never removed. The branch is kept.
    - First it checks the worktree for work that would be lost (`topicResolveCheck`): changes not committed, commits not on any remote, commits not merged into the default branch. If there is any, a form lists it: Enter resolves anyway (`git worktree remove --force`), Escape keeps the topic. The core refuses without `force` too.
19. Beside **Path** at the top right are three git buttons (`topic.checkout`, `topic.master`, `topic.push`; no keys). Each acts on where the topic works now: its newest path, or else where it last ran (`where`). The *base repo* is the repo its worktree is of (`repo`), or else the one its directory is in. Each says what it did, or why not, as a toast.
    - **Check out**: the worktree's commit, checked out detached in the base repo (git will not check out a branch that another worktree has). Only with a worktree.
    - **Master**: the default branch (the remote's, else `master`) checked out in the base repo.
    - Both are refused while the base repo's checkout has changes not committed.
    - **Push**: `git push -u origin <branch>` from the worktree (or the directory): the branch, made on GitHub if new; never forced. Refused on a detached HEAD, on the default branch, to an `origin` not on GitHub, and while Claude answers. Then the branch's PR, if it has one, joins the topic (17).

20. **Where the box sends.** By default, Enter in the box adds a note. **Tab** in the box goes to the next place it can send, then back to a note (`topic.target`, `sendTargets`). The places come from the Slack items in the chat, each once, in the chat's order:
    - A message in a thread: a reply in that thread.
    - A message in a conversation: a reply in its thread, or a message to the conversation.
    - A conversation (a pasted `…slack.com/archives/<channel>` link): a message to it.
    - A message that has not loaded yet gives no place, because the app cannot tell if it is in a thread.
21. While the box sends to Slack, it has the warning's colours (`--warning-soft`, `--warning-line`), and the Slack mark and the conversation's name (with "thread" for a thread) are on its right. Enter sends the text to Slack as me, and links the message into the chat (`Core.topicSlackSend`). Then the box goes back to a note, so a second Enter cannot send again. If the send fails, the text comes back. Ctrl+Enter with text in the box does not send it to Claude: it says why (`dispatchRefusal`). The choice is not persisted: after a restart, the box adds a note.
22. **Only I send to Slack** (`docs/slack.md`). `chat.postMessage` is the only write. Only a call with `byMe` (`api.ts`) can make it, and only `Core.topicSlackSend` gives `byMe`. That method is not in `Core.actions`, so the phone, the MCP server and Claude cannot call it. Only the window's own IPC channel (`slackSend`) calls it, and the window sends only immediately after a key press or click of mine (`navigator.userActivation`). The core sends only to a place that a Slack item in the topic gives.
23. **Waits.** A topic's `wait` is a list of what it waits on: `{ slack, since, dismissed? }`. `slack` is a conversation (`slack:conv:…`) or a thread (its first message). `since` is when the wait started (Unix ms). Later kinds of wait go beside `slack`.
    - On a hover over a Slack message in the chat, buttons show: wait on its **Thread**, its **Channel**, or **Both** (`topicWait`). A conversation in the chat shows **Wait**.
    - What came into a wait (`waitCandidates`): in a conversation, its top-level messages; in a thread, its replies. Only the ones after `since`. Not mine, not one already in the topic, not one I dismissed, not a join or a leave.
    - A topic is **waiting** (`waiting`) when it has waits and nothing came into any of them. `.` does not go to a waiting topic. In the list, a waiting topic shows `⧗`.
    - It is worked out from the cache, so it needs no polling of its own: the Slack watch (every 15 s) puts every new message there.
24. Above the box of a topic with waits is a box of them (`TopicWaits`): for each wait, the Slack mark, the conversation or thread, and how long it has waited (or how many new messages there are), and a × that stops it (`topicUnwait`). Under each wait are the messages that came in: **Add** links one into the topic; **Dismiss** keeps it out (`topicDismiss`). When I add or dismiss all of them, the topic waits again, until I remove the wait.

## Key decisions

- **A message is a note, not a new type.** The MCP server reads it as any note. The chat does not select it, so the item tools do not work on it there.
- **The chat is flat.** No notes under messages, so Enter needs no meaning on the rows: it moves the keyboard between the box and the chat.
- **The response marks the dispatch.** The messages to send are the notes after the newest response. No other marker is necessary.
- **Topics is also a module.** Its root is in `moduleViews`, so the classic UI shows it in the sidebar, and a headless caller can use it. The classic UI shows a topic as its chat too (`Detail`).
- **A wait is read off the cache, not polled.** The watch already finds every new message across Slack; a poll per conversation would break the rule that the app never polls conversations one by one.
- **A wait is up while something new is not handled.** When I add or dismiss what came in, it waits again; it stops only with ×.
- **The phone stays on the classic UI.** It can open a topic and dispatch (the tool has a label), but it cannot make a topic.
